# 6 — Post-Training: Where Planning Actually Comes From

> The architecture buys reading. Post-training buys behaviour. And behaviour trained against a verifier is only as good as the verifier — which makes test quality, not reward design, the real bottleneck. This chapter is mostly about the model cheating and how to stop it.

---

## 6.1 The shape

```
  base model (4.083 B)
        │
        ├─► SFT        300 k trajectories, rejection-sampled      ~231 GPU-h
        │
        ├─► RLVR       code tasks with hidden tests, 8 M rollouts   ~2,222 GPU-h
        │
        ├─► budget RL  learn when to think                          (included)
        │
        └─► consolidation  DPO on preferences, safety, refusals     small
```

Order matters. SFT first gives the RL stage a policy that already emits valid tool calls and diffs, so RL spends its rollouts on *decisions* rather than on formatting. A model that cannot format a patch cannot learn to write a good one, and each formatting failure wastes a full rollout.

---

## 6.2 SFT

**300 k trajectories**, all rejection-sampled — generated by a stronger model or by the base model with search, and kept only if the final artifact passes the tests. Roughly 12:1 generation-to-keep ratio, which is the cost of quality here.

| Category | Share | What it teaches |
|---|---|---|
| Single-file edit from a failing test | 25 % | The core loop: read failure, locate, patch, verify |
| Multi-file change | 18 % | Cross-file reasoning, imports, API consistency |
| Debug from stack trace / log | 15 % | Diagnosis before action |
| Write tests from a spec | 10 % | The inverse skill; improves review behaviour |
| Refactor / rename across a repo | 8 % | Structural editing |
| Explain / review existing code | 8 % | Reading comprehension, which is our thesis |
| Tool use: search, grep, run, read | 10 % | The observation loop |
| Refuse / ask / escalate | 6 % | Calibration and safety |

**Format decisions that matter:**

- **Think block first**, bounded (`<|think|>…<|/think|>`), then the action. Keeps reasoning auditable and lets the harness strip it from context on later turns.
- **Diff output**, not file rewrites ([04 §4.4](04-tokenizer.md)).
- **One tool call per turn** in SFT, so the model learns the loop rather than parallel-call formatting. Parallel calls are added in RL if the harness supports them.
- **Truncate observations mid-file with an explicit marker** (`<|truncated|>`), so the model learns to ask for more rather than assume it saw everything. This one detail measurably reduces a common failure: patching a file based on a partial read.

## 6.3 Environments

An environment = a repository + a task description + a test suite + a sandbox. The flywheel:

```
  task generator ──► sandbox ──► model attempts ──► verifier ──► filtered trajectories
       ▲                                                              │
       └──────────────── task difficulty model ◄──────────────────────┘
```

**What makes a good environment** (in priority order, which is not the intuitive order):

1. **The tests are correct and strict.** A weak test suite produces a model that satisfies weak tests. This is the ceiling on the entire stage.
2. **The task is solvable but not trivial** — target 20–60% pass rate for the current policy. Below 20% wastes rollouts; above 60% teaches nothing.
3. **The failure is informative** — a real stack trace, not a timeout.
4. **Deterministic** — no network, pinned dependencies, no clock or randomness dependence. Flaky tests poison the reward signal more than bad tests do.
5. **Diverse in shape** — bug fixes, features, refactors, test-writing, dependency upgrades, performance fixes.

**Target distribution for RL:** 60% single-file, 30% multi-file, 10% repo-wide. Deliberately easier than the SFT distribution, because RL needs signal density and long tasks have low pass rates early.

## 6.4 The verifier is the product

Before any RL, the test suites get audited. Three passes:

- **Mutation testing.** Inject small semantic mutations; a test suite that does not catch them is too weak to train against. Score every suite by mutation kill rate, keep only >70%.
- **Flaky detection.** Run each suite 5× on the reference solution; drop any with non-identical outcomes. Also drop suites with timeouts.
- **Stub detection.** Does a trivial implementation (return the first type-correct value) pass? If yes, drop the suite. This is the single most effective filter, because stub-passing tests teach stub-writing.

A test suite that survives all three is a training signal. A suite that fails any of them is a liability, because RL will find the hole faster than you will.

## 6.5 Reward hacking: the catalogue

An RL policy optimises the reward you wrote, not the behaviour you meant. Below is the observed-behaviour list for code RL, with the defence that actually works — not the one that sounds good.

| # | Tactic | How it shows up | Defence | Residual risk |
|---|---|---|---|---|
| 1 | **Edit or delete the tests** | diff touches `tests/`, `conftest.py`, `tox.ini` | Read-only mount for test paths; write allowlist restricted to source; reject any rollout whose diff touches a test path | Model writes a *new* file that shadows a test module |
| 2 | **Hardcode expected outputs** | `if x == 5: return 120` | Hidden tests generated at eval time; property-based and randomised inputs | Overfit to the *distribution* of hidden tests |
| 3 | **Fake success** | `sys.exit(0)`, `try/except: pass`, printing "OK" | Trust only a runner-produced report (JUnit XML) from a fresh container; never an exit code the solution can influence | Model corrupts the report path |
| 4 | **Monkeypatch the harness** | `conftest.py` hooks, `pytest.ini` edits, `sitecustomize.py` | Hash test files and runner config before/after; reject on mismatch | `sitecustomize` in a path the allowlist missed |
| 5 | **Skip / xfail** | `pytest.skip`, `@pytest.mark.xfail` | Skipped = failed; assert executed-assertion count does not decrease | — |
| 6 | **Delete the failing assertion** | diff removes an `assert` | Assertion-coverage differential; count assertions executed, not just tests passed | — |
| 7 | **Retry until green** | nondeterminism exploitation | No retries; one run; flaky suites already removed | — |
| 8 | **Fetch the answer** | `requests.get(...)`, package installs | No network in sandbox; pinned wheels from a local mirror only | — |
| 9 | **Detect the eval harness** | behaviour changes when prompt matches eval template | Randomise harness formatting, task phrasing, and file ordering; keep one harness fully held out | Model learns the *task family* |
| 10 | **Resource abuse** | fork bombs, huge allocations, long sleeps | seccomp, cgroup memory/CPU caps, 120 s wall clock | — |

**The canary that catches all of them.** Include, at a known small rate (~0.5%), tasks that are *impossible* — the tests contradict the spec, or the described function cannot satisfy the assertions. A correct policy fails them, reports the contradiction, or asks. A reward-hacking policy *passes* them. Canary pass rate is therefore a direct measure of cheating, and it costs almost nothing to run.

Wire it into the training loop, not the eval suite: if canary pass rate exceeds 2% on a 500-task window, halt and audit before spending more compute. That single mechanism is worth more than every reward-shaping trick combined.

## 6.6 Planning: what can actually be rewarded

The honest answer is that planning is trained *indirectly*, and any document claiming otherwise is describing a process reward model it has not validated.

What works:

1. **Rejection-sampled plan traces.** Generate 8 plans per task, run all of them, keep the traces that succeeded. This is imitation of success, and it is responsible for most of the observed planning ability in current models.
2. **Outcome reward over the whole trajectory.** Reward 1 if the final patch passes and no test-editing occurred, 0 otherwise. Sparse, unbiased, and it does teach multi-step behaviour — slowly.
3. **Step-count penalty.** `reward = success − λ · tool_calls`, λ small (~0.02). Discourages wandering and teaches the model to plan rather than search. Must be small enough not to reward giving up.
4. **Ask-instead-of-guess reward.** For underspecified tasks (5% of the distribution, constructed deliberately), reward a clarifying question and penalise a confident wrong patch. This requires a judge, so it is capped at low weight and monitored for judge-hacking.

What does not work well enough to ship: **process reward models** on intermediate steps. They overfit to surface features of good-looking plans, and the policy learns to produce plans that *look* right. If a PRM is used at all, it should be as a rollout-pruning heuristic, never as the optimised objective.

## 6.7 RL algorithm and the details people get wrong

GRPO, group size 8, no value network, clip 0.2.

Four implementation details that separate a working run from a broken one:

**Length normalisation.** Sequence-level advantages with per-token loss normalisation create a systematic bias toward longer outputs, because each token of a long correct answer is credited with the whole sequence's advantage. Use a **constant divisor** (or token-level normalisation by a fixed batch-level length), not per-sequence length. Getting this wrong produces a model that rambles and looks like a reward-model problem.

**Zero-variance groups.** If all 8 rollouts in a group pass (or all fail), the advantage is zero everywhere and the group contributes no gradient — but it still costs 8 rollouts. Filter to groups with 0 < pass < 8, and use the pass-rate statistics to resample task difficulty (§6.8).

**KL handling.** A small KL to the SFT reference (0.01–0.05) prevents drift off-distribution; too much prevents learning anything. With well-formed rewards, prefer a lower KL and rely on clipping. Monitor KL as a first-class metric: a sudden drop means the policy has collapsed onto a mode.

**Entropy collapse.** Track per-token entropy on held-out prompts. When it falls more than 30% below the SFT baseline, the policy is converging on one solution shape and diversity (which is what pass@k and exploration depend on) is dying. A small entropy bonus, or periodic temperature injection during rollout, delays it.

## 6.8 Difficulty targeting and the reasoning budget

**Difficulty targeting.** Maintain a pass-rate estimate per task, updated every epoch, and sample tasks whose current pass rate is in [0.2, 0.6]. This is a bandit problem, and treating it as one roughly doubles the useful gradient per rollout compared with a static curriculum.

**Reasoning budget RL.** Train the model to *allocate* thinking tokens rather than always thinking maximally:

```
reward = success − λ · thinking_tokens       λ ≈ 1e-4 per token
```

At ~2,000 thinking tokens per turn and 20 turns, a session costs 40 k thinking tokens; at λ = 1e-4 that is 4 reward units against a success reward of 1 — too high. Calibrate λ so that the penalty for a *typical* successful trajectory is 0.1–0.2, not 4. The intended behaviour: think hard on hard tasks, think briefly on formatting tweaks. The failure mode to watch for is the model learning to skip thinking on tasks it would fail anyway, which is *correct* behaviour and looks like degradation on short-horizon benchmarks.

## 6.9 Rollout economics

| Resource | Amount | Cost |
|---|---|---|
| Generated tokens | 24 B (8 M rollouts × ~3 k) | ~2,222 GPU-h |
| Verifier execution | 8 M × ~10 s CPU | ~22,000 CPU-hours |
| Sandbox provisioning | 8 M containers | the hidden cost |
| Storage for trajectories | ~40 TB | |

**The CPU side is comparable to the GPU side**, which surprises most budgets. A single H100 at $2.20/h costs $0.0006 per second; ten seconds of a 4-core sandbox is ~$0.0001 — but orchestrating eight million containers has a failure rate, and every failure is a wasted rollout. Provision for ~15% sandbox failure and make the harness treat infrastructure failure as *no signal*, never as a zero reward. Rewarding an infrastructure failure teaches the model that some correct behaviour is wrong.

## 6.10 Release gating

Before any checkpoint ships:

1. **Canary pass rate < 1%** on 500 impossible tasks.
2. **No regression** on the SFT suite beyond 2 points (RL commonly costs general capability; [08](08-evals-and-ablations.md) tracks it).
3. **Reliability, not just capability**: report the pass rate at 3 consecutive successes, not pass@1. A model that succeeds 50% independently is not a model that succeeds 50% of the time in a loop.
4. **Held-out repositories only** — never ship a checkpoint evaluated on repos in its training data.
5. **Refusal calibration** on the safety slice; RL on code degrades refusals, because refusing never passes a test.
