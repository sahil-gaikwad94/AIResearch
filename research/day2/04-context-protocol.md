# 4 — The Context Protocol

> The highest-leverage document in day 2, and it contains almost no machine learning. Prefix caches are content-addressed by *all* preceding tokens, so a single rewritten byte invalidates everything after it. An agent that appends deltas instead of re-rendering state turns an 8,000-token-per-turn problem into a 600-token one — and never invalidates anything.

---

## 4.1 The mechanism that decides everything

Both production engines key the cache the same way:

```
key(block) = hash(tokens_before_the_block ‖ tokens_in_the_block)
```

vLLM states it plainly: each KV block "can be uniquely identified by the tokens within the block and the tokens in the prefix before the block." SGLang's radix tree does the same thing structurally, and extends it to copy-on-write branching plus a three-tier hierarchy.

The consequence is a property nobody designs around until it bites:

> **Changing token `k` invalidates every cached block from `k` to the end of the context.**

Not "reduces the hit rate". Invalidates. If your harness re-renders a 400-token file at token 120,000 of a 200,000-token context, you re-prefill 80,000 tokens — and you do it again next turn.

Day 1 noticed this ("compaction destroys prefix caches") and responded with a request to the harness. Kestrel-2 responds with a format.

---

## 4.2 The protocol

**Invariant: the token stream is append-only for the life of a session. Nothing already emitted is ever rewritten.**

Everything an agent needs to say is expressible as an append:

| Event | Naive harness | Append-only protocol |
|---|---|---|
| Read a file | insert 400 tokens of file body | insert 400 tokens, once, never again |
| Edit a file | re-render 400 tokens in place | append `<|patch|>` + 40-token diff |
| Delete code | re-render | append the diff |
| Run tests | insert output | insert output |
| Change your mind | rewrite the plan | append `<|revise|>` + the correction |

A three-line change to a 400-token file costs **40 tokens and zero invalidation**, instead of 400 tokens and 80,000 tokens of re-prefill.

### The wire format

```
<|file|>src/api/routes.py
<|content|>
from .models import User
@router.get("/u/{id}")
def get_user(id: int):
    ...
<|end|>

<|exec|>pytest tests/test_routes.py -q
<|out|>
FAILED tests/test_routes.py::test_404 - assert 200 == 404
<|end|>

<|patch|>src/api/routes.py
@@ def get_user(id: int):
-    return User.get(id)
+    u = User.get(id)
+    if u is None:
+        raise HTTPException(404)
+    return u
<|end|>
```

Every reserved token here already exists in the day-1 vocabulary ([04 §4.2](../day1/04-tokenizer.md)); the only addition is `<|revise|>`.

### Why the model must be trained on it

A protocol the model has never seen is a prompt-engineering trick that degrades under distribution shift. The model has to learn three specific things:

1. **A patch supersedes earlier content.** When it sees `<|patch|>f.py` and a diff, it must treat the patched region as current — without the file being re-rendered. This is *state tracking over an event log*, and it is trainable.
2. **Old content is still ground truth for what was true then.** Debugging often needs the pre-patch version.
3. **Absence of a patch means the file is unchanged.** The model must not assume staleness.

Training data for this is generated by construction: take a repository's commit history, replay it as a stream of file-reads and patches, and the supervision is free. That is [06 §6.5](06-training.md), and it is one of the cheapest high-value data sources in the project.

## 4.3 The arithmetic

Day 1's session model: 30 k start, 8 k new per turn, 20 turns, 190 k unique, 1.04 M tokens re-sent without caching.

Kestrel-2's session model on the same task:

| Quantity | Day 1 | Day 2 |
|---|---|---|
| Initial context (repo prefix) | 30 k | 30 k (or 400 k for a monorepo) |
| New tokens per turn | 8,000 | **600** |
| Turns before compaction | ~4 | none |
| Cache invalidations | 1 per compaction | **0** |
| Unique tokens prefilled | 190 k | 190 k (same work, done once) |
| Tokens prefilled *per turn* | 8,000 | **600** |
| Context at turn 20 | 64 k after 4 compactions | 42 k and never compacted |

At a 400 k-token monorepo prefix the difference is starker: day 1 must compact repeatedly to stay under 64 k, and each compaction both loses information and invalidates the cache. Kestrel-2 reads all 400 k at 7,168 tokens per layer and never compacts.

### Where the time goes

| Stage | Day 1 | Day 2 | Why |
|---|---|---|---|
| Prefill per turn | 900 ms (8 k new) | **25 ms** (800 new @256 k) | 10× fewer tokens × 3.8× cheaper each |
| Decode per turn (600 tok) | 0.97 s | 0.75 s | weights-bound at both |
| Re-prefill after compaction | 3.7 s, every ~5 turns | **never** | no invalidation |
| **Model time per turn** | **~1.9 s** | **~0.5 s** | |

And the tail, which is where the real damage was: a harness that rewrites a file once every twenty turns pays an *expected* 4,000 tokens of re-prefill per turn on top of everything else — 6× the protocol's steady-state cost, for one bad habit.

## 4.4 Ordering, when a rewrite is unavoidable

Sometimes a rewrite is genuinely unavoidable: a formatter rewrites a file, a tool regenerates a lockfile, a user pastes new content. In that case the invalidation cost is the **suffix length**, so ordering is a lever:

```
[stable: system prompt, repo map, dependency roots]  ← never changes
[read-only: files opened once]
[volatile: files edited this session]                ← put these LAST
```

If the 400-token file that changes lives at token 190,000 of 200,000, a rewrite costs 10,000 tokens of re-prefill. If it lives at token 150,000, it costs 50,000. **Ordering volatile files last is a free 5× reduction on the tail**, and no model change is required to get it.

The rule generalises: *sort the context by expected mutation frequency, ascending.*

## 4.5 The cache as a published artifact

The second systems consequence, and it is bigger than the first.

A 400 k-token repository prefix is identical for every session, every user, and every agent in a swarm working on that repository at that commit. Its KV is therefore not per-session state — it is a **build artifact**: computed once, content-addressed, shared, and versioned by the repository's commit.

| | Day 1 (per session) | Day 2 (per repo) |
|---|---|---|
| 400 k prefix | 400 k × 20 KiB = 8.2 GiB **per session** | 4.6 GiB **once** |
| 32 concurrent sessions | 262 GiB — impossible | 4.6 + 32 × (64 k × 11 KiB) = **26.6 GiB** |
| Sessions per 80 GB GPU | ~3 at 400 k | **~64** |

That is the number that changes the deployment. SGLang reports the production version of this: multi-turn hit rates near 98%, and input throughput rising 15.5× when a third cache tier is added.

The engineering requirements are unglamorous and entirely standard:

- **Content-addressed blocks** (hash of tokens, not of file paths);
- **Copy-on-write branching** for per-session deltas;
- **A tier hierarchy**: HBM → host DRAM → NVMe, with the repo prefix pinned at the cheapest tier that meets latency;
- **Invalidation by commit**, not by file — a new commit publishes a new artifact and lets the old one drain;
- **Isolation**: a `cache_salt` per tenant, so one customer's repository KV is never readable by another's hash match.

## 4.6 Failure modes

| Failure | Symptom | Fix |
|---|---|---|
| A tool rewrites rather than appends | hit rate collapses to ~0 mid-session | wrap the tool; diff its output against previous state and emit a patch |
| The harness re-renders the system prompt with a timestamp | hit rate 0 at turn 2 | strip all nondeterminism from the prefix; this is the single most common bug |
| Context grows past 1 M in a long session | OOM or truncation | cap the append stream; on overflow, **fork** a new session with a fresh outline rather than compacting in place |
| Anchors go stale | the model patches based on an old signature | anchors are keyed by content hash; a changed file invalidates only its own outline block |
| Replay ordering differs between sessions | cache misses across users | canonical file ordering (sorted by path) for the shared prefix; only the per-session tail may vary |

That last row is worth stating as a rule:

> **The shared prefix must be a pure function of (repository, commit).** Anything else — session id, user id, timestamp, random file order — makes the artifact unshareable.

## 4.7 Why this is worth more than the architecture

A rough decomposition of the per-turn cost reduction from day 1 to day 2:

| Change | Effect on per-turn prefill tokens | Effect on decode time |
|---|---|---|
| Sparse attention | — | 2.2× at 256 k |
| Append-only deltas | **13×** (8,000 → 600) | — |
| No compaction | removes a 3.7 s stall every ~5 turns | — |
| Shared repo cache | 64 sessions/GPU instead of 3 | — |

The protocol is the largest single factor, and it required no parameters, no kernels, and no training beyond replaying commit history.

> An architecture document that ignores its own I/O format is optimising the second-largest term.
